1Cross-cutting UI principles

Five principles apply to every screen in the stack; persona sections state only what is specific to them.

P1 — Every number can explain itself. Every displayed price, Greek, vol, or P&L figure is stamped with its lineage — MarketSlice, surface epoch and sub-version, curve-set epoch, model name and version — reachable by hover or click. The engine's explain capability is a UI affordance, not a batch tool: "why is this number what it is" costs one gesture, everywhere. This single principle eliminates the largest category of production support traffic.

P2 — State is visible, and degraded state is loud. The quality flags that flow through the engine (degraded surface, stale forward, overridden pillar, tier disagreement, error-budget breach) render as a consistent visual language across all screens: same colors, same iconography, same semantics on a trader blotter as on an ops console. A number derived from flagged inputs inherits the flag visibly. Nothing degrades silently, and nothing shouts when healthy.

P3 — The rings are visible in the chrome. Every interactive control belongs to a ring, and the UI renders the difference structurally. Ring-3 operational actions (override, widen, pull, kill) are immediate but framed: entitlement-gated, reason-captured, auto-expiring, with the audit record shown as it is created. Ring-2 changes (pair definitions, model selection, tolerances) are never direct edits — the UI drives a promotion workflow: draft → semantic diff → golden-replay impact report → approvals → staged activation. Ring-1 items (models, strategies) surface read-only: name, version, link to documentation. A user can tell what kind of thing they are touching by how the control looks.

P4 — Time travel is universal. Every screen accepts an as-of: flip any blotter, surface view, or risk matrix to its exact state at 14:32:07 last Tuesday, reconstructed from journals and epochs. Incident review, dispute resolution, and audit all reduce to "open the screen, set the clock." Live mode is simply as-of = now, continuously advancing.

P5 — UIs are consumers, not calculators. No screen computes its own truth: every UI subscribes to the same epochs, slices, and journals as any other consumer. Two screens showing the same number at the same as-of show the same value, bit-for-bit, or one of them is wrong in a way the platform can detect. Screen-side computation is limited to presentation (sorting, bucketing for display, chart scaling).

3Trader / market-maker

Mission. Price incoming interest, keep the surface marked where the market is, and know the book's risk at all times. The trader's screens are the only ones where sub-second update latency is a hard requirement and keyboard-first operation is non-negotiable: a pricer that requires a mouse is a pricer that loses the trade.

Screen: Pricer / deal ticket

Single-instrument pricing with full first-gen coverage. Requirements: instrument entry in desk shorthand (typed, parsed, echoed back in full — eurusd 3m 1.0850 ko 1.1200 10 should price without a mouse); live PV and Greeks off the current slice with the price ticking as the market moves; the model badge (P3: which named model, which version, per the selection matrix) and the slice stamp (P1) always visible; bid/offer construction shown decomposed — mid, spread, skew adjustment — never as an unexplained number; what-if panel with spot/vol/date bumps computed against the same contracts as risk, not a screen-side approximation (P5); one-keystroke booking into the trade journal with the priced slice attached, so the risk system and the eventual P&L explain agree with what the trader saw at execution (wireframe W1).

W1 — Trader pricer. Shorthand-in, decomposed bid/offer, model badge and slice stamp always on, what-if computed by the same pricing contracts as risk. Booking journals the trade with the slice it was priced on.

Screen: Surface manager

The desk's view of every pair's smile: fitted surface against raw market quotes per pillar, fit residuals, arb-gate status per tenor, and the re-anchor/recalibration state (which regime, per P2, is always visible). Ring-3 mark actions live here: override a pillar's ATM/RR/BF with mandatory reason, automatic expiry, and immediate downstream flag propagation — the trader sees, at entry time, the same override banner every consumer will see (wireframe W2). Event-vol editing (weights on identified dates) is Ring 3 with tight bounds; changing the event calendar itself is Ring 2 and routes to the promotion workflow. Requirements: side-by-side compare of any two epochs or any epoch vs live; per-pillar quote provenance (which sources, which composite weights); explicit display of what recalibration is waiting on when the surface is stale.

W2 — Surface manager. Fit vs market with residual flags, per-pillar override entry that shows its audit consequence at entry time, arb-gate status, and the two-speed state (epoch + sub-version) always visible.

Screen: Position & risk blotter

The book, bucketed the way the desk thinks: by pair, then tenor bucket, with delta / gamma / smile-bucket vega (ATM, RR, BF per tenor) / vanna / volga / theta columns, drill-down to position level, and the two-speed machinery made honest (P2): each row shows its revaluation freshness — error-budget consumption as a small meter, last full reval time — so the trader knows which numbers are Taylor-tracked and which are freshly exact (wireframe W4). Barrier proximity is a first-class display: positions within a configured band of their trigger sort to the top with distance-to-level and the tightened budget state. Spot-ladder × vol matrix per pair on demand, computed by the batch path, stamped with its slice.

W4 — Position & risk blotter. Smile-bucket vega columns, per-row freshness meters exposing the Taylor/full-reval regime, barrier proximity as a first-class panel, and drill-through to any number's explain.

4e-Trading supervisor

Mission. Keep automatic quoting competitive when the world is normal and safe when it is not. This persona's UI is dominated by Ring-3 controls and by the mechanical couplings of decision D6: the console's job is to make the automatic behavior legible and the manual overrides immediate.

Screen: Quoting console

One row per pair (wireframe W3): streaming state (streaming / auto-widened / pulled, with the reason when automatic — "surface degraded", "forward stale"), current spread vs base, inventory skew direction, quote age, hit ratio and volume this session. Controls, all Ring 3 — entitled, reason-captured, expiring: widen by factor, pull pair, size cap, master kill. The master kill is deliberately prominent and deliberately unceremonious: it must be pressable in under a second at 3 a.m. — ceremony is for the un-kill, which requires a reason and, above a duration threshold, a second pair of eyes. Requirements: every automatic state change (quality-flag-driven widening) appears in the same event stream as manual actions, so "why were we wide for 40 minutes" has a scrollable answer; RFQ tape with per-quote slice stamps and win/loss against the eventual print where known.

W3 — e-Trading console. Automatic quality-driven state changes are legible (state + reason + rule), kill is one gesture while un-kill carries ceremony, and the RFQ tape ties every quote to the slice that priced it.

5Sales & structuring

Mission. Price and present to clients without being able to move the desk's marks. Sales sees prices, never mark inputs: the persona is read-only against the pricing core plus a workflow of its own. Requirements: client-terms pricer (premium in either currency, client-convention deltas, strategy packages priced as packages); sales margin entry on top of the desk price, with margin visible to the desk and to product control but not blended invisibly into "the price"; RFQ workflow — request to desk, desk response, client-facing presentation — with the full chain journaled; indicative vs firm state made explicit on every displayed price, with firm prices carrying expiry countdowns. Entitlement note: sales entitlements are the template for external-facing surfaces later (client portal), so the read-only projection of the pricing core is designed once, here.

6Market data operations

Mission. The inputs are clean, or the right people know they are not. This persona owns the layer that everything else depends on, and their console is the system's early-warning radar.

Screen: Feed & quality console

Per-pair, per-quote-kind health grid (spot, forwards, each vol pillar × source): freshness against class tolerances, composite dispersion across sources, quarantine counts with reason codes, CIP-residual and triangulation monitors with trend sparklines (wireframe W5 shares the pattern). Ring-3 actions: demote/promote a source in a composite, force-quarantine an instrument, relax a staleness tolerance for a declared window (bounded, expiring — the illiquid-session case). Requirements: the override inventory — every live Ring-3 mark and data action across the whole stack, who, why, when it expires — lives here as a single queryable view, because scattered overrides that nobody can enumerate are how yesterday's judgment becomes next year's mystery; quarantine review queue with one-gesture release/extend; direct pivot from any alert to the affected downstream objects ("this stale forward feeds these three surfaces, these two are already degraded").

7Quant / methodology owner

Mission. Know that calibration is healthy today and make it better tomorrow, without either activity endangering production. The quant's surfaces split cleanly along that line: diagnostics (read-only, live) and evolution (Ring-2 proposals, sandboxed).

Screen: Calibration lab

Fit diagnostics per pair per epoch: residuals by pillar, arb-gate margins (not just pass/fail — how close), solver iteration trends (the early-warning signal for a deteriorating regime), fast-path vs slow-path agreement over time, model basis (stream vs official model) by instrument class. Requirements: full history, not just current — every diagnostic is a time series; cross-pair comparison; export to the quant's research environment with lineage preserved.

Screen: Replay lab & champion/challenger

The replay harness with a UI: pick any window, rerun it under a candidate configuration or strategy version, and see the semantic diff — surfaces, prices, risk — against what production did. Challenger strategies run continuously against live inputs in shadow (no publication), with standing dashboards of challenger-vs-champion divergence. When a challenger graduates, the same screen produces the Ring-2 promotion package: the diff, the impact report, the evidence — feeding directly into the change console (§9, wireframe W6). Requirement: the lab is the only path by which candidate methodology touches market data, and it is structurally incapable of publishing — the sandbox is an architecture property surfaced as a UI property.

8Market risk manager

Mission. An independent, complete view of exposures against limits, on their own cadence, with the power to ask any what-if. Risk consumes the same epochs as everyone (P5) but views them on snapshot cadence: coherent slices at fixed times, plus on-demand. Requirements: the trader's risk blotter, re-cut by risk's hierarchies (desk, book, currency, tenor) with limits and utilization inline, breaches and warnings driving a worklist with acknowledgment workflow; scenario workbench — spot/vol matrices, historical stress dates, custom scenario authoring saved as governed definitions (scenario definitions are Ring 2: reviewed, versioned, shared); concentration views FX risk actually needs: barrier-density maps (notional of triggers within bands of current spot, per pair — where does the book's gamma flip), event-date vega concentration, pin risk at expiry clusters; full drill from any aggregate to positions to a single trade's pricing explain (P1) without leaving the screen. The risk manager explicitly does not get mark or model controls — independence of the view is the point — but does get annotation: attach a note to any number, visible to the desk, journaled.

9Model validation & governance

Mission. Control what is allowed to price, mark, and hedge — with evidence. This persona's primary surface is the change console (wireframe W6): the Ring-2 promotion workflow rendered as a queue. Each pending change — model selection matrix edit, pair definition change, strategy version bump, tolerance adjustment — presents as a package: the semantic diff in domain terms ("barriers on G10 pairs: VV-2.3 → SLV-1.0 for official"), the golden-replay impact report (P&L impact distribution across the live book, positions breaching materiality flagged), the requester's rationale, and the approval chain state. Approvals are structural four-eyes minimum, with the approval itself journaled and the activation staged (effective from the named epoch, never "now"). Requirements: the model inventory — every named strategy, version, approval status, where the matrix uses it, links to validation documents; scheduled revalidation as a worklist with aging; and the reverse query, which auditors always ask and systems rarely answer: "show me everything priced by model X version Y between these dates" — answerable because every PricingResult carries its model stamp (P1).

W6 — Change console. Every Ring-2 promotion arrives as a package: semantic diff in domain terms, golden-replay impact with materiality flags, rationale and evidence, four-eyes approval chain, epoch-staged activation.

10Middle office / trade support

Mission. Every booked trade is right, and every lifecycle event happens exactly once. Requirements: trade blotter over the trade journal with full amendment history visible per trade (the journal is the audit trail — the UI just renders it); a lifecycle workstation for the events FX options generate — expiries with exercise decisions (auto vs manual per configuration, with cut-time countdowns), barrier and touch monitoring (proximity watchlist, then a determination workflow when a level trades: the fixing source, the print, the determination, and the resulting booking, all journaled — barrier disputes are won and lost on this record), fixings for settlement, delivery vs cash flows; breaks dashboard reconciling internal state against confirmations and settlement systems, with aging and ownership; bulk operations (portfolio expiry processing at cuts like NY 10 am / Tokyo 3 pm) with preview-then-commit semantics. Amendments are journaled events under entitlement, with materiality-based four-eyes: a notional correction re-prices and re-explains automatically, and the P&L impact of the amendment is shown before commit.

11Product control / IPV

Mission. Sign the P&L and prove the marks. Two surfaces. P&L explain: daily and intraday attribution — delta, gamma, vega by smile bucket, theta, rates, new trades, amendments, model basis, unexplained — where every attribution term is computed from the same journaled slices the desk traded on (P5), and unexplained above tolerance opens a drill-down, not an argument: the explain decomposes per position, and P1 takes it from there. IPV workbench: month-end (and spot-check) comparison of desk marks against independent sources — consensus services, broker quotes — with variance by pair/tenor/parameter, materiality-weighted worklists, adjustment proposals with their P&L impact precomputed, and the sign-off record. The official EOD marks workflow lives with this persona: the candidate official epoch (snapped by configured rules), diffs against yesterday and against live, exceptions flagged, then a journaled approval that stamps the epoch official — the same epoch machinery, with a governance bit only this persona can set.

12Platform operations (SRE)

Mission. The machine is healthy, and when it is not, the blast radius is chosen deliberately. The system console (wireframe W5): end-to-end latency SLOs per path (spot→grid, RFQ, vol→epoch, reval-wave lag) as live percentile meters with budget-burn alerts; epoch flow per pair (surface epoch age, expected vs actual cadence, curve-set epoch consumption lag); journal health (append rates, replication lag, replay-determinism spot checks — the nightly replay-and-compare rendered as a scoreboard); component topology with the dependency graph live-colored by state. Ring-3 controls with the heaviest framing in the stack: freeze publication (per pair / global), promote secondary (the deterministic-twin failover), enter degraded mode, halt reval waves. Freeze and failover are four-eyes above configured scope. Requirement discipline: every control here states its blast radius in consumer terms before commit — "freezing EURUSD publication stalls 2 auto-quoting pairs and 3 dependent crosses" — because 3 a.m. decisions are made at the level of what the button says.

W5 — Platform console (shared pattern with the market-data quality console). Latency budgets, epoch flow with click-through to root cause, feed health, and Ring-3 controls that state their blast radius in consumer terms before commit.

13Audit, compliance & management

Audit & compliance get one read-only surface: the audit explorer — cross-journal search (quotes, trades, overrides, config promotions, approvals, operational actions) with the time-travel affordance (P4) as its core interaction: reconstruct any screen any participant saw at any moment, from journals, with the reconstruction itself evidential. Entitlement reporting (who can do what, who did what, exceptions) is a standing report, not an annual archaeology project. Management (desk head, COO delegates) get a glanceable summary: P&L, risk vs limits, quoting posture per pair, open overrides past a threshold age, pending Ring-2 approvals aging, system health rollup — every tile a door into the owning persona's screen, no numbers computed specially for management (P5 again: the summary is a projection, not a parallel truth).

14Non-functional requirements

ConcernRequirement
Update latency, trading screensTick-to-glass ≤ 250 ms for pricer/blotter/quoting console; visible-value conflation (a cell repaints at most ~4×/s, always showing latest) rather than event queues per P5.
Update latency, control screensSnapshot cadence 5–60 s, configurable; explicit "as-of" timestamp on every control-function screen — control personas must never mistake a snapshot for live.
Keyboard & densityTrader and MO screens: full keyboard operation, desk-shorthand entry, high-density grids (30+ rows without scrolling on desk monitors). Control screens optimize for comprehension over density.
Multi-monitor & layoutDetachable panels, saved named layouts per user, layouts follow entitlements (a screen you lose access to disappears from your layout, with notice).
Follow-the-sunAll times zone-explicit (desk default, UTC on hover); cut-time logic (NY 10am, Tokyo 3pm) rendered in both local and desk time; handover view: open overrides, pending approvals, degraded state, annotated for the incoming region.
EntitlementsSingle entitlement service for all surfaces; UI renders only what the user may do (no disabled-button archaeology); every write action carries user, reason where required, and entitlement context into the journal.
ResilienceUIs are stateless against the bus: reconnect and replay-to-current on any disconnect; a UI restart never loses an in-flight Ring-3 action ambiguously — actions are acknowledged journaled or visibly failed.
Accessibility & themingStatus semantics never carried by color alone (P2 iconography); light/dark themes with identical semantics; font scaling without layout collapse.

15Build order

UI phases track the engine's phases, with control surfaces deliberately early rather than last: Phase 1 — surface viewer and calibration diagnostics (read-only), because the first thing built needs eyes on it; the explain affordance (P1) built into the component library from the first screen, not retrofitted. Phase 2 — trader pricer, surface manager with Ring-3 marks, quoting console, feed console: the minimum set for a desk to stream safely. Phase 3 — risk blotter with two-speed honesty, MO lifecycle workstation, replay lab, change console: the governance spine goes live with the first-gen book, not after it. Phase 4 — P&L explain and IPV workbench, audit explorer, management summary, follow-the-sun handover. The principle: a persona whose screens arrive late will have built spreadsheets in the gap, and the spreadsheets will still be there in five years — screen debt is config debt's front-office cousin.
